# ADR-0011: 원문 본문은 열 때 뽑아 보여 주고 저장하지 않으며, 번역은 버튼으로 만들어 따로 저장한다

- 상태: 수용
- 결정일: 2026-09-29
- 관련: ADR-0003, ADR-0012

## 배경

지금 화면은 Entry 제목을 누르면 원문이 새 탭에서 열린다(`apps/web/src/entry-card.tsx`의 `href={entry.url}`).
앱 안에서 내용을 읽을 수 없고, 보여 줄 수 있는 것도 요약뿐이다. 요약은 "원문 본문을 저장하지 않는다"는 Entry 정의를 지키려고
태그를 걷어내고 500자로 자른 평문이다(`apps/backend/src/collector/handlers/summary-text.ts`의 `SUMMARY_MAX_LENGTH`).
정보원 원본인 `raw`는 API로 내보내지 않는다(ADR-0003).

또 Feed 대부분이 영어라 한국어로 훑고 싶다. 번역은 DeepL 무료 API(월 50만 자)를 쓸 수 있고, 브라우저에서 직접 부를 수 없어 백엔드를 거쳐야 한다.

## 결정

1. **원문 추출은 열 때 한다**: Entry를 펼친 화면에서 읽기 버튼을 누르면 백엔드가 `entry.url`의 페이지를 가져와
   defuddle(버전 고정)과 linkedom으로 본문을 Markdown으로 뽑아 돌려준다. 자동으로 가져오지 않는다.
2. **추출 결과는 저장하지 않는다**: DB에도 메모리에도 두지 않는다. 같은 Entry를 다시 열면 다시 가져온다.
   Entry는 여전히 링크와 메타데이터이고, 요약 500자 상한도 그대로다.
3. **페이지를 가져오는 방법**: 수집기의 `httpClient`(ofetch)가 아니라 undici `request`에 브라우저와 비슷한 헤더를 붙여 보낸다.
   리다이렉트는 따라가고, 타임아웃은 15초, HTML은 5MB까지 받는다. 수집기 코드는 바꾸지 않는다.
4. **실패 판정**: HTTP 상태가 200이 아니거나, 타임아웃이거나, 추출한 본문이 비었을 때만 실패로 보고 원문 링크와 함께 알린다.
   짧거나 엉뚱한 내용이 나와도 추출된 그대로 보여 준다.
5. **렌더링**: `react-markdown`에 `rehype-raw`와 `rehype-sanitize`(기본 허용 목록, GitHub README 렌더링 규칙)를 쓴다.
   `<img>`·`<table>`·`<details>`는 남고 `<script>`·이벤트 속성·인라인 `<svg>`·`<iframe>`은 버려진다.
6. **읽기 버튼을 숨기는 Feed**: Product Hunt와 OpenRouter. 추출은 되지만 본문이 아니라 제품·대시보드 화면이 나온다.
   이 목록은 화면이 정하는 값이라 웹 쪽 표에 둔다.
7. **번역은 버튼으로 만든다**: Entry를 펼친 화면의 번역 버튼을 누르면 백엔드가 제목과 요약을 DeepL로 한국어 번역한다.
   목록 제목을 자동으로 번역하지는 않는다(ADR-0012에서 제안). 원문 본문은 번역하지 않는다.
8. **번역은 따로 저장한다**: `entry_translation`(키 `entry_id`, `title`, `summary`, `translated_at`)에 Entry와 1:1로 저장한다.
   번역이 있으면 DeepL을 다시 부르지 않는다. 목표 언어는 한국어 하나라 언어 컬럼은 두지 않는다.
   Entry 조회 응답은 번역 제목·요약을 함께 내려 주고, 목록은 번역이 있으면 번역 제목만 보여 준다.
9. **DeepL 키**: 환경 변수 `DEEPL_API_KEY`. 없으면 번역 버튼이 번역할 수 없다고 알린다.

## 검토한 대안들

### 원문을 iframe으로 띄운다

- 장점: 백엔드 작업이 없다.
- 단점: GitHub, OpenAI, TechCrunch처럼 `X-Frame-Options`로 막는 사이트가 많아 빈 화면이 된다.
- 기각 사유: 주요 정보원 상당수에서 동작하지 않는다.

### 수집할 때 본문을 저장한다

- 장점: 열 때 기다리지 않고, 원문이 사라져도 남는다.
- 단점: Entry 정의와 요약 상한을 뒤집는다. 수집마다 원문 페이지 요청이 Entry 수만큼 늘고, 읽지 않을 글까지 저장한다.
- 기각 사유: 대부분의 Entry는 제목만 보고 넘긴다. 읽는 소수를 위해 모두를 긁을 이유가 없다.

### defuddle.md 호스팅 서비스를 부른다

- 장점: 페이지 가져오기와 파싱 코드가 없다.
- 단점: 키 없이 IP당 월 1,000회, 가용성 보장 없음, 읽는 모든 주소가 제3자에게 간다.
- 기각 사유: 라이브러리로 돌려도 한 페이지에 수십~수백 ms라 외부 서비스에 기댈 이득이 작다.

### 추출 결과를 메모리에 잠깐 캐시한다

- 장점: 같은 글을 다시 열 때 빠르다.
- 단점: 같은 글을 다시 여는 일이 드물다.
- 기각 사유: 필요해지면 그때 붙여도 되는 크기다.

### 번역을 `entry` 컬럼으로 둔다

- 장점: JOIN이 없다.
- 단점: `entry`는 정보원에서 가져온 것과 사용자의 읽기 상태를 담는다. 번역은 우리가 만든 파생 데이터이고, 자동 번역을 붙이면 실패 수 같은 자기 상태가 생긴다.
- 기각 사유: 성격이 다른 데이터를 나눠 두는 편이 ADR-0012의 확장에도 맞다.

### Markdown 안의 HTML을 모두 버린다(`skipHtml`)

- 장점: 설정이 가장 단순하다.
- 단점: GitHub README의 로고, 표, 접기가 사라져 저장소 상세가 망가진다.
- 기각 사유: HN·Show HN은 누구나 올린 페이지로 가므로 걸러야 하지만, 버릴 필요까지는 없다. GitHub이 검증한 허용 목록으로 충분하다.

## 이유

"Entry는 링크와 메타데이터"라는 정의를 지키면서 앱 안에서 원문을 읽는 방법은 열 때 가져오는 것뿐이다.
defuddle 확인(2026-09-29, Feed마다 실제 URL로 추출)에서 기술 뉴스·블로그·GitHub README·논문 페이지는 깔끔하게 나왔고,
실패는 NYT·reddit·YouTube·X와 본문 없는 웹앱에 몰렸다. 실패해도 원문 링크로 가면 되므로 저장해 둘 이유가 없다.

번역은 비용(월 한도)이 드는 파생 데이터라 한 번 만든 것은 저장해 다시 쓴다. 목록 제목이 짧아 원문으로도 읽힌다는 판단이라,
먼저 버튼으로만 만들고 자동 번역은 써 본 뒤에 정한다. 버튼과 자동 번역은 같은 저장소와 같은 DeepL 호출을 쓰게 된다.

## 결과

- 원문을 읽을 수 있는지는 정보원 사이트에 달려 있다. 운영 서버(데이터센터 IP)에서는 Cloudflare가 로컬보다 더 막을 수 있다.
- 같은 글을 열 때마다 원문 사이트에 요청이 간다. Indie Hackers처럼 응답이 느린 사이트는 몇 초 걸린다.
- Opened At은 원문 링크뿐 아니라 앱에서 Entry를 펼친 것으로도 찍힌다(CONTEXT.md). Read Cursor 규칙도 이를 따른다.
- 새 의존성: 백엔드 `defuddle`·`linkedom`·`undici`, 웹 `react-markdown`·`rehype-raw`·`rehype-sanitize`·`@tailwindcss/typography`.
- 배포 환경에 `DEEPL_API_KEY`가 필요하다. 없으면 번역만 빠지고 나머지는 동작한다.
