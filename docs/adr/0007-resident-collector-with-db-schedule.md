# ADR-0007: 수집기는 상주 컨테이너 하나로 두고, 스케줄은 DB가 소유한다

- 상태: 수용
- 결정일: 2026-09-24
- 관련: ADR-0001, ADR-0008

## 배경

Feed마다 수집 주기가 다르고, 운영하면서 주기를 바꿀 수 있어야 한다. 수집기가 멈춰도 화면은
동작해야 한다. 로컬(macOS, Windows)과 배포(Ubuntu)에서 같은 방식으로 실행돼야 한다(ADR-0001).

## 결정

1. **실행 방식**: 수집기는 저장소 안의 상주 컨테이너 하나로 실행한다. 백엔드(API)와는 별도 프로세스다.
2. **이미지**: 백엔드와 수집기는 Dockerfile 하나를 공유하고 target만 나눈다(`app`, `collector`).
   `collector` 이미지에는 화면 빌드 결과를 넣지 않는다. 그래서 화면만 바뀐 배포에서는 수집기가
   재시작되지 않는다.
3. **Feed의 원본**: Feed는 코드의 선언 파일로 만든다. 앱이 시작될 때 DB에 없는 Feed만 넣는다.
   한 번 들어간 뒤로 주기 같은 운영 값은 DB가 소유하며, 코드가 덮어쓰지 않는다.
4. **스케줄**: Feed 행의 `next_run_at`이 스케줄의 유일한 상태다. 수집기는 `next_run_at ≤ 지금`인 Feed를
   하나씩 순차 실행한다.
5. **비정상 종료 정리**: 수집기가 시작할 때 `running`으로 남은 Fetch Attempt를 `failed`로 바꾼다.

## 검토한 대안들

### 호스트 cron

- 장점: 스케줄러를 만들 필요가 없다.
- 단점: 호스트 설정이 저장소 밖에 있다. Windows 로컬에서 같은 방식으로 돌릴 수 없다.
- 기각 사유: ADR-0001 결정 1(호스트에 의존하지 않는다)과 충돌한다.

### API 프로세스 안의 스케줄러

- 장점: 컨테이너가 하나 준다.
- 단점: 수집이 멈추거나 느려지면 화면도 함께 영향을 받는다. 화면을 배포할 때마다 수집도 끊긴다.
- 기각 사유: 수집기가 죽어도 화면은 멀쩡해야 한다.

### Jenkins 주기 Job (one-shot)

- 장점: 스케줄링을 기존 도구에 맡긴다.
- 단점: 배포 도구가 운영 스케줄러를 겸한다. 로컬에서는 같은 방식으로 돌릴 수 없다. Feed마다 다른
  주기를 표현하기 어렵다.
- 기각 사유: 로컬과 배포의 실행 경로가 갈라진다.

### Feed 정의 전체를 코드가 소유

- 장점: 원본이 한 곳이다.
- 단점: 주기를 바꿀 때마다 재배포해야 한다.
- 기각 사유: 주기는 운영하면서 조정하는 값이다.

### Feed 정의 전체를 DB가 소유

- 장점: 배포 없이 Feed를 추가하고 수정할 수 있다.
- 단점: Feed를 추가하는 쓰기 경로(화면이나 SQL)가 생긴다. Handler 파라미터처럼 코드와 맞물린 값이 코드
  밖에 놓인다.
- 기각 사유: Feed를 추가하는 일은 대개 Handler 작업과 함께 오므로 코드 쪽이 자연스럽다.

## 이유

상주 프로세스가 하나뿐이면 같은 Feed를 두 번 집어 들 일이 없다. 그래서 DB 잠금이나 선점 없이
`next_run_at` 하나로 스케줄을 표현할 수 있다. Feed 수십 개를 각각 10초 안에 수집하는 규모에서는
순차 실행으로 충분하다. 스케줄 상태가 DB에 있으므로 수집기가 재시작돼도 이어서 실행된다.

## 결과

- 수집기 컨테이너를 두 개 이상 띄우면 안 된다. 그렇게 해야 할 상황이 오면 `SELECT … FOR UPDATE SKIP LOCKED`
  같은 선점 방식으로 바꾸는 새 결정이 필요하다.
- 선언 파일의 기본 주기를 바꿔도 이미 있는 Feed에는 반영되지 않는다. 기존 Feed의 주기는 DB에서 바꾼다.
- Feed 식별자는 한 번 정하면 바꾸지 않는다. 바꾸면 기존 Entry와 연결이 끊긴 새 Feed가 된다.
- 선언에서 뺀 Feed는 더 이상 수집되지 않지만 데이터는 남는다.
- 한 바퀴를 도는 시간이 가장 짧은 주기보다 길어지면 Feed 사이의 동시 실행을 검토한다.
