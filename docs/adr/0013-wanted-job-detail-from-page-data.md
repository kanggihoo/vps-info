# ADR-0013: 원티드 공고 상세는 열 때 페이지에 실린 공고 데이터를 읽어 Markdown으로 보여 준다

- 상태: 수용
- 결정일: 2026-09-30
- 관련: ADR-0003, ADR-0006, ADR-0011

## 배경

원티드 Feed는 목록 API로 제목·회사·지역·경력·고용 형태만 받는다(`apps/backend/src/collector/handlers/wanted-handler.ts`).
자격 요건, 주요 업무, 우대 사항, 채용 전형, 복지, 기업 자체 채용 사이트 주소(`out_link`)는 공고 상세 페이지(`/wd/<id>`)에만 있다.
원티드 상세는 Next.js Pages Router가 서버에서 그려 보내며 같은 내용을 HTML의 `__NEXT_DATA__`(`props.pageProps.initialData`)에 싣는다.
그래서 개발자 도구에서 페이지에 직접 진입했을 때는 별도 API 요청이 보이지 않는다.

ADR-0011의 읽기 버튼은 원문 페이지를 defuddle로 긁는다. 원티드 상세는 화면이 지원 UI가 붙은 SPA라 그 방식이 맞지 않아 읽기 버튼을 숨겼었다.
Entry는 링크와 메타데이터이고 원문 본문을 저장하지 않는다는 정의(CONTEXT.md)는 유지해야 한다.

## 결정

1. **열 때 읽는다**: 원티드 Entry의 읽기 버튼을 누르면 백엔드가 `entry.url`의 페이지를 가져와 `__NEXT_DATA__`의 공고 데이터로 Markdown을 만든다. 수집할 때는 상세를 받지 않는다.
2. **본문은 저장하지 않는다**: ADR-0011과 같다. 같은 공고를 다시 열면 다시 가져온다. 요약 500자 상한도 그대로다.
   **마감일만 예외로 저장한다**: 상세 데이터에 마감일(`due_time`)이 있으면 `ReaderView.deadline`(`YYYY-MM-DD`)으로 돌려주고, 같은 요청에서 그 Entry의 `entry.extra.deadline`에 jsonb로 합쳐 넣는다.
   마감일은 수집 목록에 없어서, 사용자가 연 공고부터 목록 카드에 마감이 보이게 하려는 것이다. 마감이 연장될 수 있어 열 때마다 최신 값으로 덮어쓴다. 마감일이 없는 공고는 `extra`를 건드리지 않는다.
3. **새 API나 응답 타입을 만들지 않는다**: 기존 `GET /api/entries/:entryId/reader`와 `ReaderView`를 쓴다. `readOriginal`이 원티드 공고 주소(`https://www.wanted.co.kr/wd/<id>`)이면 defuddle 대신 `readWantedJob`(`apps/backend/src/server/wanted-job-page.ts`)을 부른다.
4. **보여 주는 순서**: 고용 형태·원격 근무 → 기업 채용 사이트 지원 링크(`out_link`가 http(s)일 때만) → 자격 요건 → 주요 업무 → 우대 사항 → 채용 전형 → 혜택 및 복지 → 회사 소개.
5. **기술스택 태그는 만들지 않는다**: 페이지 데이터에는 기술스택 필드가 없고, 자격 요건 글에 적혀 있는 경우가 많다. 별도 내부 API(`chaos/jobs/v4/<id>/details`)는 웹이 쓰는 경로가 아니라서 기대지 않는다.
6. **읽기 버튼은 원티드에서 보인다**: 웹의 읽기 버튼 숨김 목록(`reader-availability.ts`)에 원티드는 넣지 않는다.

## 검토한 대안들

### 수집할 때 새 공고마다 상세 API를 불러 기술스택과 요약을 저장한다

- 장점: 카드에 기술스택 태그가 붙고, 열 때 기다리지 않는다.
- 단점: 첫 수집에서 공고 수(약 340건)만큼 요청이 나가고, 읽지 않을 공고까지 받는다. 웹이 쓰지 않는 내부 API에 기댄다.
- 기각 사유: 대부분의 공고는 제목만 보고 넘긴다(ADR-0011과 같은 판단).

### 원티드 전용 API 라우트와 응답 타입을 새로 만든다

- 장점: 섹션을 구조화된 필드로 내려 화면이 자유롭게 그릴 수 있다.
- 단점: 라우트, 타입, 화면 컴포넌트가 늘고 다른 채용 사이트마다 반복하게 된다.
- 기각 사유: Markdown 하나로 충분히 읽히고, 다른 정보원에도 같은 읽기 버튼 흐름을 쓸 수 있다.

## 이유

`__NEXT_DATA__`는 사이트가 자기 화면을 그리려고 싣는 데이터라, 내부 API나 화면 구조(클래스 이름)보다 덜 바뀐다(Trendshift Handler와 같은 접근).
기존 읽기 흐름에 끼워 넣으면 화면·API·타입이 바뀌지 않고, Entry가 링크와 메타데이터라는 정의도 지킨다.

## 결과

- 원티드가 Next.js 구조나 `initialData` 필드 이름을 바꾸면 상세가 `empty`로 실패한다. 실패해도 원문 링크로 갈 수 있다.
- 공고 내용은 "ㆍ"로 시작하는 줄이 이어진 평문이라 목록이 아닌 줄은 줄바꿈만 지킨 문단으로 보인다.
- 마감일은 수집 목록(chaos)에 없고 상세 페이지에만 있다. 그래서 **열어 본 공고만** 목록 카드에 마감이 보이고, 열지 않은 공고는 마감을 모른다. 마감이 있는 공고는 일부(약 15%)다.
- 앱(server)이 `entry.extra`를 쓰는 경로가 처음 생긴다. 수집기는 이미 있는 Entry의 `extra`를 다시 쓰지 않으므로(Dedup 충돌 시 건너뜀) 서로 덮어쓰지 않는다.
- 마감이 지난 공고는 카드에 `마감`으로 보인다(한국 시각 기준, 마감일 당일까지는 진행 중). 목록에서 마감 공고를 걸러 내지는 않는다.
- 페이지 가져오기는 ADR-0011의 `fetchOriginalPage`를 그대로 쓰므로 내부망 주소 차단이 적용된다.
