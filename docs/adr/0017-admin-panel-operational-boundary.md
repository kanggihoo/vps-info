# ADR-0017: 관리자 패널은 Feed 운영을 제어하고 외부 연동 상태를 조회한다

- 상태: 수용
- 결정일: 2026-10-02
- 관련: ADR-0004, ADR-0005, ADR-0014, ADR-0015, ADR-0016

## 배경

운영자는 한 명이며, 기존 읽기 화면과 별도의 페이지에서 수집 주기를 조정하고 오류를 확인하려 한다.
현재 Feed의 운영 주기는 DB가 소유하지만 관리 API는 없다(ADR-0004, `apps/backend/src/server/feed-routes.ts:34`).
Fetch Attempt에는 성공·실패, 시작·종료 시각, 새 Entry 수, 오류 메시지가 저장된다(`apps/backend/src/db/schema.ts`의 `fetchAttempt`).
수집기는 기한이 된 Feed를 하나씩 기다리며 실행한다(`apps/backend/src/collector/feed-scheduler.ts:48`).
현재 상태 확인 API는 DB 연결만 검사하며 수집기 응답 여부를 확인하지 않는다(`apps/backend/src/server/build-server.ts:43`).

원문 읽기는 요청 시 본문을 가져오며 본문을 저장하지 않는다. LLM 호출 이력도 DB에 저장하지 않는다.
DeepL 번역에는 API 키를 사용하므로, 호출 이력을 새로 쌓는 대신 공식 사용량 API에서 현재 사용량과 한도를 확인할 수 있다.
접속은 사용자가 운영하는 nginx Basic Auth로 이미 제한한다. nginx 설정은 이 저장소 밖에서 관리한다.

## 결정

1. **Feed 운영**: 관리자 페이지에서 수집 상태와 Fetch Attempt 이력을 조회하고 주기 변경, 수동 수집 요청, 일시정지, 재개를 제공한다.
2. **일시정지**: 자동 수집과 자동 재시도를 중단하되 수동 수집은 허용한다. 진행 중인 수집은 마치고, 재개하면 한 번 수집한 뒤 정상 주기로 돌아간다.
3. **원티드 예외**: 맥에서 수집을 깨우는 기존 방식(ADR-0014)을 유지하며, 일반 Feed의 주기 설정과 분리한다. 상태·수집 이력 조회와 수동 수집만 제공하고 주기 편집 및 일시정지·재개는 제공하지 않는다.
4. **LLM 관찰**: 연결 상태만 확인한다. 이 패널을 위해 호출 이력이나 대화 내용을 DB에 저장하지 않는다.
5. **DeepL 관찰**: 서버가 공식 `GET /v2/usage`를 호출해 사용량과 한도를 조회한다. 번역 호출마다 별도의 운영 이력을 저장하지 않는다.
6. **원문 읽기**: 관리자 패널의 관찰 대상에서 제외한다.
7. **접속 인증**: 기존 nginx Basic Auth를 사용하며 앱 내 별도 로그인을 추가하지 않는다. 관리자 페이지와 관리 API도 이 인증 범위에 둔다.
8. **관리 경계**: 서버·컨테이너·배포·백업 제어와 Feed 추가·삭제·Handler 파라미터 변경은 포함하지 않는다.
9. **실행 동시성**: 현재 수집기 하나가 Feed를 순차 실행하는 구조를 유지한다(ADR-0004).
10. **주기 변경 적용**: 기존 `computeNextRunAt`에 현재 연속 실패 수, 새 주기, 변경 시각을 전달해 다음 실행 시각을 다시 계산한다. 정상 상태는 변경 시각에 새 주기를 더하고, 실패 상태는 새 주기를 상한으로 한 기존 백오프를 적용한다. 연속 실패 수는 초기화하지 않는다. 변경 전에 화면에서 적용될 다음 실행 시각을 보여준다. 즉시 수집은 별도의 수동 요청으로 처리한다.
11. **수동 수집 요청**: 기존 수집기가 처리하며 다른 Feed가 실행 중이면 기다린다. 같은 Feed가 요청 대기 또는 실행 중이면 중복 요청을 받지 않는다. 화면에 요청됨, 실행 중, 성공·실패를 표시한다.
12. **화면 구성**: 상단에 수집기 상태, LLM 연결 상태, DeepL 사용량·한도를 두고 본문에 Feed별 상태, 주기, 최근 성공, 다음 실행, 조치 버튼을 둔다. Feed를 선택하면 수집 이력과 오류 상세를 보여준다. 원티드는 별도 구역에 상태와 예외 실행 방식을 표시한다.
13. **진입 링크**: 기존 읽기 화면의 Bookmark 아래에 `관리` 링크를 둔다. 모바일에서는 기존 상단 가로 메뉴에서 접근한다.
14. **수집기 상태 확인**: 수집기의 마지막 응답 시각과 현재 실행 중인 Feed를 표시한다. 응답이 오래 갱신되지 않으면 `수집기 응답 확인 안 됨`으로 경고하며, 프로세스 종료로 단정하지 않는다. 주기 대기, Feed 수집 실패, 수집기 응답 없음은 구별한다.
15. **수집기 응답 기록**: 30초마다 마지막 응답 시각을 기록하고, 2분 이상 갱신되지 않으면 응답 확인 안 됨으로 표시한다. 한 번도 기록이 없으면 아직 응답 기록이 없다고 표시한다.
16. **화면 갱신**: 관리자 화면을 보는 동안 수집 상태를 10초마다 갱신한다. LLM 연결 상태와 DeepL 사용량은 화면 진입 및 `새로고침` 버튼으로 조회한다.
17. **이력 조회**: 선택한 Feed의 최신 Fetch Attempt 50건부터 표시하며, 이전 기록 조회와 성공·실패 필터를 제공한다. 이 패널을 위해 기존 수집 이력의 보관 정책을 바꾸지 않는다.

## 검토한 대안들

### 모든 외부 호출 이력을 DB에 저장한다

- 장점: 원문 읽기·번역·LLM의 과거 오류와 소요 시간을 한곳에서 조회할 수 있다.
- 단점: 기록 스키마와 보관 정책이 필요하며, 현재 원하는 연결 상태·사용량 확인보다 범위가 넓다.
- 기각 사유: 원문 읽기 기록은 필요하지 않고, LLM은 연결 상태, DeepL은 공식 사용량 조회면 충분하다.

### Feed 정의까지 관리자 화면에서 편집한다

- 장점: Feed를 추가하거나 Handler 파라미터를 바꿀 때 배포를 생략할 수 있다.
- 단점: 코드가 소유하던 Feed 정의의 편집 경로가 DB로 옮겨가 ADR-0004의 소유권 구분이 달라진다.
- 기각 사유: 현재 필요한 것은 기존 Feed의 운영 값과 실행 상태 제어다.

## 이유

이미 저장하는 Fetch Attempt를 활용하고, 외부 서비스는 필요한 상태만 조회하면 새 기록 체계를 만들지 않고 운영 요구를 충족할 수 있다.
Feed 정의와 운영 값의 소유권을 유지하고, 원티드의 기기 의존 실행을 일반 주기 설정으로 바꾸지 않는다.

## 결과

- LLM과 원문 읽기의 과거 오류를 이 패널에서 조회할 수는 없다.
- 일시정지는 주기를 길게 늘리는 방식이 아닌 명시적인 상태로 표현해야 한다.
- Basic Auth 적용 범위는 관리자 화면과 API를 함께 포함해야 한다.
- DeepL 사용량은 계정 기준일 수 있으며, 서비스 자체의 번역량으로 단정하지 않는다. 응답이 제공하는 계정·키 구분을 따른다.
- 느린 Feed를 실행하는 동안 다른 Feed의 수집은 기다린다. 관리자 패널의 수동 수집 요청도 이 순차 실행 제약을 따른다.
- 수집기 상태 확인은 긴 수집이 진행 중인 동안에도 응답 시각이 갱신되도록 해야 한다. 수집이 끝난 시각만으로 생존 여부를 판정하지 않는다.
- 실패한 Feed의 수집 주기와 다음 재시도까지의 간격은 서로 다를 수 있다. 화면에서 주기와 다음 실행 시각을 구별해 표시한다.
- 수동 요청 시각과 Fetch Attempt 시작은 같은 Feed 행을 잠근 트랜잭션에서 이어진다. 수집 중 바뀐 운영 스케줄은 버전을 비교해 완료 처리가 덮어쓰지 않는다.

DeepL API 근거: [Check usage and limits](https://developers.deepl.com/api-reference/usage-and-quota/check-usage-and-limits).

## 구현 체크리스트

- [x] Feed에 일시정지·수동 요청·스케줄 변경 버전을 추가하고 수집기 응답 테이블을 마이그레이션한다. 새 테이블·컬럼에는 DB COMMENT를 넣는다.
- [x] 수집 직전 Feed 상태를 다시 확인하고 수동 요청 소비와 Fetch Attempt 시작을 원자적으로 처리한다. 수집 완료가 운영 중 변경한 다음 실행 시각을 덮어쓰지 않도록 변경 버전을 비교한다.
- [x] 수집기 응답을 긴 수집과 독립적으로 30초마다 기록하고 종료 시 기록을 정리한다.
- [x] `/api/admin` 아래에 Feed 상태·이력, 주기 변경·일시정지·재개·수동 요청, 수집기 상태와 DeepL 사용량 API를 추가한다. LLM 연결 확인은 기존 `/api/llm/models`를 재사용한다.
- [x] `#/admin` 화면과 Bookmark 아래 진입 링크를 추가한다. 수집 상태는 10초 갱신, 이력은 50건 페이지와 성공·실패 필터를 제공한다.
- [x] 일시정지·중복 요청·수집 중 설정 변경·원티드 제한·이력 페이지를 DB 통합 테스트로 확인한다. DeepL 조회는 가짜 HTTP 응답으로 검증한다.
- [x] 타입 검사, 전체 단위 테스트, DB 통합 테스트, 화면 빌드와 브라우저 확인을 완료한다.

## main 통합

2026-10-03에 PR #3이 병합된 main을 반영했다. Feed 순서 저장·키보드 탐색과 관리자 기능을 함께 유지하며, journal은 0008 다음 0009 순서로 둔다.
0009 snapshot은 Feed Navigation Order와 관리자 운영 상태를 모두 포함하며 prevId는 0008 snapshot의 id를 가리킨다. 이미 배포된 0008과 관리자 0009의 SQL 및 적용 timestamp는 변경하지 않는다.

- Drizzle 검사 통과. 통합 스키마를 다시 generate해도 추가 마이그레이션이 생성되지 않는다.
- main의 0000~0008만 적용한 DB에 Feed 순서를 저장한 뒤 0009를 적용해 기존 순서 데이터 유지와 관리자 컬럼 기본값을 확인했다.
- 브라우저에서 읽기 패널의 숫자 키 탐색, Entry 열기, 키보드 순서 이동과 선택 유지, 관리자 전환을 확인했다. 관리자 주기 입력의 방향키는 숫자 입력을 변경하며, 저장·새로고침 후 Feed 순서와 운영 값이 함께 유지된다.
