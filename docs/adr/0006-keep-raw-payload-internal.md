# ADR-0006: Entry에 정보원 원본(`raw`)을 보존하되 API로 노출하지 않는다

- 상태: 수용
- 결정일: 2026-09-24

## 배경

수집 방식은 RSS, 공식 API, HTML 스크래핑으로 제각각이고, Feed마다 고유한 필드가 있다(HN 점수와
댓글 수, 모델 다운로드 수 등). 이 필드들을 모두 공통 컬럼으로 만들 수는 없다. 게다가 Entry는
영구 보관하고(삭제 정책 없음) 변경은 감지하지 않는다. 그래서 수집 시점에 버린 정보는 나중에 되살릴 수 없다.

## 결정

1. **저장 구조**: 모든 Feed가 쓰는 필드는 공통 컬럼으로 둔다. Feed에만 있는 필드 중 화면에 쓰는
   것은 `extra`(JSONB)에 둔다. 정보원이 준 원본은 `raw`(JSONB)에 그대로 보존한다.
2. **`raw`의 공개 범위**: `raw`는 내부 전용이다. API 응답에 포함하지 않는다.
3. **조회 규칙**: `SELECT *`를 쓰지 않는다. 조회할 컬럼을 명시한다.

## 검토한 대안들

### `raw`를 저장하지 않는다

- 장점: 저장 용량이 작고 스키마가 단순하다.
- 단점: Handler가 파싱할 때 빠뜨린 필드는 영영 복구할 수 없다.
- 기각 사유: 영구 보관 시스템에서 수집 시점의 정보 손실은 되돌릴 수 없다.

### `raw`까지 API로 노출한다

- 장점: 화면에서 원하는 필드를 바로 꺼내 쓸 수 있다.
- 단점: 정보원의 응답 형식이 API 계약의 일부가 된다. 정보원이 형식을 바꾸면 화면이 깨진다.
  응답 크기도 커진다.
- 기각 사유: 정보원 형식과 화면 사이의 완충층인 `extra`가 무의미해진다.

## 이유

`raw`는 파싱 실수에 대비한 보험이다. `extra`는 화면과 맺는 계약이다. 둘을 나누면 정보원 형식이 바뀌어도
Handler만 고치면 되고, 과거 Entry는 `raw`에서 `extra`를 다시 계산할 수 있다.

## 결과

- Entry 한 행이 공통 컬럼보다 크다. 목록 조회에서 `raw`를 읽지 않도록 컬럼을 명시해야 한다.
- 화면에 새 필드가 필요하면 Handler가 `extra`를 채우도록 고친다. 과거 Entry는 `raw`로 다시 채울 수 있다.
