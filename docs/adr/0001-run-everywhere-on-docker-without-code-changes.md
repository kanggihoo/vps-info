# ADR-0001: 모든 구성요소를 Docker로 실행하고 로컬과 배포 사이에 코드 차이를 두지 않는다

- 상태: 수용
- 결정일: 2026-09-22

## 배경

이 프로젝트는 개발자 한 명이 로컬 macOS(arm64)에서 개발하고 Ubuntu(amd64) VPS에 배포한다.
두 환경이 갈라지면 "로컬에서는 되는데 배포에서 안 되는" 문제가 생기고, 그때마다 코드를 고쳐
맞추면 로컬과 배포 중 한쪽은 항상 검증되지 않은 코드를 돌리게 된다.

작성 시점 기준으로 현재 코드는 이 목표를 네 곳에서 어기고 있다.

1. **로컬과 배포가 서로 다른 아티팩트를 실행한다.** `compose.local.yml`이 frontend를
   `target: development` + `npm run dev`(Vite dev server)로 교체한다. 배포는
   `frontend/Dockerfile`의 최종 스테이지인 nginx 정적 서빙이다. 같은 이미지가 아니다.
2. **`/api` 라우팅 메커니즘이 환경마다 다르다.** 로컬은 `frontend/vite.config.ts`의
   `server.proxy`가, 배포는 `vps-infra`의 상위 Nginx가 처리한다. `frontend/nginx.conf`에는
   `/api` location이 없어서, 이 저장소의 프로덕션 이미지만으로는 API 호출이 완결되지 않는다.
   (프론트엔드 코드 `frontend/src/api.ts`는 상대경로 `/api/...`만 쓰므로 코드 차이는 없다.)
3. **저장소 단독으로는 어느 환경에서도 뜨지 않는다.** `compose.yml`의 `vps_proxy`·`vps_data`가
   `external: true`이고 PostgreSQL 서비스가 없다. `README.md` 1단계가 `vps-infra`를 먼저
   실행하도록 요구한다.
4. **마이그레이션만 Docker 밖에서 돈다.** `README.md` 3단계가 호스트에서
   `uv run alembic upgrade head`를 실행하므로 호스트에 uv와 Python 3.12가 필요하다.
   `Dockerfile`은 이미 `alembic.ini`와 `alembic/`을 COPY하고 있어 컨테이너 실행이 가능한데도
   `compose.yml`에 해당 서비스가 없다.

이 ADR은 지켜야 할 규칙을 확정한다. 위 네 곳을 **어떻게** 해소할지는 아키텍처 재구조화에서
정하며, 각 항목은 `decisions-later.md`에 열린 질문으로 남겨 두었다.

## 결정

1. **실행 수단**: 모든 구성요소(Backend, Frontend, Collector, 마이그레이션)는 Docker 컨테이너로
   실행한다. 호스트에 언어 런타임(Python, Node, uv)이 설치돼 있을 것을 요구하지 않는다.
2. **환경 차이의 표현 수단**: 로컬과 배포의 차이는 환경변수와 Compose override 파일로만
   표현한다. 환경을 분기하는 코드(`if ENV == "local"` 류)나 환경별 소스 브랜치를 두지 않는다.
3. **빌드 위치**: 이미지는 그 이미지가 실행될 대상 위에서 빌드한다. 로컬 macOS에서 빌드한
   arm64 이미지는 amd64 배포 서버에 사용하지 않는다.
4. **지원 환경의 범위**: 로컬은 macOS(arm64), 배포는 Ubuntu(amd64) 두 가지만 지원한다.
   Windows는 고려하지 않는다.

## 검토한 대안들

### 모든 이미지를 `platform: linux/amd64`로 고정

- 장점: 로컬에서 빌드한 이미지를 그대로 배포에 쓸 수 있다. 빌드 결과가 환경과 무관하게 동일하다.
- 단점: macOS arm64에서 amd64 빌드는 QEMU 에뮬레이션이라 매 빌드가 몇 배 느려진다.
  로컬 실행 성능도 함께 떨어진다.
- 기각 사유: 규칙의 목적은 "코드 수정 없이 어디서든 동작"이지 "같은 바이너리가 어디서든 동작"이
  아니다. 개발 중 가장 자주 반복되는 동작(빌드)에 상시 비용을 물리는 대가로 얻는 이득이
  이 프로젝트 규모에서는 없다.

### buildx로 multi-arch 이미지 빌드

- 장점: arm64와 amd64를 동시에 지원한다. 배포 대상이 늘어나도 대응된다.
- 단점: 빌드 파이프라인에 buildx 설정과 이미지 레지스트리 푸시가 필요하다.
- 기각 사유: 배포 대상이 Ubuntu VPS 한 대뿐이라 multi-arch가 해결할 문제가 아직 없다.
  배포 대상이 늘어나면 이 ADR을 대체한다.

## 이유

세 안 모두 "로컬과 배포에서 코드 수정 없이 동작"이라는 목표는 달성한다. 차이는 비용의 위치다.
`platform` 고정과 buildx는 **빌드 시점**에 비용을 지불하고 아티팩트 동일성을 얻는다.
"배포 대상에서 빌드"는 아티팩트 동일성을 포기하는 대신 비용이 없다.

이 프로젝트에서 아티팩트 동일성이 실제로 막아 주는 문제는 "로컬에서 통과한 이미지가 배포에서
다르게 동작"인데, Python과 Node는 아키텍처 의존 네이티브 확장을 쓰지 않는 한 이 위험이 낮다.
반면 빌드 지연은 개발 중 매번 발생한다. 실제 위험이 낮은 쪽을 포기하고 확실한 비용을 피한다.

## 결과

- 로컬에서 빌드한 이미지는 배포에 사용할 수 없다. 배포는 항상 배포 서버 위에서 빌드해야 한다.
- 네이티브 확장을 가진 Python·Node 패키지를 추가하면 이 결정의 전제가 깨진다. 그런 의존성을
  들일 때는 로컬과 배포 양쪽에서 빌드가 되는지 확인해야 한다.
- 호스트에서 직접 실행하는 절차(`uv run ...`)는 이 규칙 위반이다. 새 절차를 문서나 스크립트에
  추가할 때는 Compose 서비스로 만든다.
- 이후 모든 ADR과 구현은 이 규칙을 전제로 한다. 이 규칙과 충돌하는 결정을 내리려면 이 ADR을
  먼저 대체해야 한다.
- 현재 코드는 배경에 적은 네 곳에서 이 규칙과 어긋나 있다. 해소 방안은 `decisions-later.md`에 있다.
