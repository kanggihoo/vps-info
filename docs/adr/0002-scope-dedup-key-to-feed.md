# ADR-0002: Dedup Key의 판정 범위를 Feed 안으로 한정한다

- 상태: 수용
- 결정일: 2026-09-24

## 배경

같은 원문이 여러 Feed에 동시에 나타날 수 있다. 예를 들어 한 기사가 Hacker News best와
다른 RSS Feed에 함께 올라온다. 이때 Entry를 하나로 합칠지 Feed마다 따로 둘지 정해야 했다.

이 시스템은 Feed별로 분리된 시간순 리더다. 통합 피드는 없다. 읽음 상태(Read Cursor)도
Feed마다 따로 둔다. 같은 원문이라도 Feed마다 외부 ID, 순위, 점수, 댓글 수, 발견 시각이 다르다.

## 결정

1. **판정 범위**: Dedup Key는 같은 Feed 안에서만 비교한다. 같은 원문이 두 Feed에 있으면 Entry도 두 개다.
2. **Dedup Key 값**: 정보원이 고유 식별자를 주면 그 값을 쓴다. 주지 않으면 정규화한 URL의 해시를 쓴다.
3. **중복 방어 수단**: DB의 `UNIQUE(feed_id, dedup_key)` 제약과 `INSERT … ON CONFLICT DO NOTHING`으로
   막는다. 애플리케이션에서 먼저 조회해 확인하지 않는다.
4. **감지 범위**: 새로 나타난 Entry만 감지한다. 이미 있는 Entry가 바뀐 것(제목, 점수 등)은 반영하지 않는다.

## 검토한 대안들

### 전역 Dedup Key (원문 하나 = Entry 하나)

- 장점: 같은 원문이 저장소에 한 번만 있다. 여러 Feed에서 본 원문을 한 번 읽으면 모두 읽은 것이 된다.
- 단점: Entry 하나가 여러 Feed에 속하게 되어 Feed별 메타데이터(순위, 점수, 발견 시각)를 둘 곳이 따로
  필요하다. Read Cursor와 First Seen을 정렬 축으로 쓰는 것도 Feed마다 값이 달라져 복잡해진다.
- 기각 사유: Feed별로 분리해서 읽는 시스템이라 원문 단위로 합쳐 봐야 쓸 곳이 없다.

## 이유

원문 단위로 합치는 이득은 "한 번 읽으면 모든 Feed에서 읽음"뿐이다. 이 시스템에는 통합 피드가 없으니
그 이득이 거의 나타나지 않는다. 반면 합치는 비용(Entry와 Feed의 N:M 관계, Feed별 관찰값 분리)은 모든
쿼리에 붙는다.

## 결과

- 같은 원문이 Feed 수만큼 중복 저장된다. 링크와 메타데이터만 저장하므로 용량 부담은 작다.
- 한 Feed에서 연 원문도 다른 Feed에서는 Opened At이 비어 있다.
- 원문 단위로 합쳐야 할 필요가 생기면 "원문(Content)"과 "Feed별 관찰(Entry)"을 분리하는 모델로
  옮겨야 한다. 이 ADR을 대체하는 결정이 된다.
- 이미 저장된 Entry의 변경을 반영하려면 `DO NOTHING`을 `DO UPDATE`로 바꾸는 새 결정이 필요하다.
