# ADR-0019: 읽기 버튼으로 가져온 본문은 저장하고, 읽음 신호를 따로 기록한다

- 상태: 수용
- 결정일: 2026-10-14
- 관련: ADR-0003, ADR-0011, ADR-0013, 이슈 #9

## 배경

나중에 "사용자가 무엇에 관심 있는지"를 판단하는 AI에게 선호 근거를 넘기려 한다. 지금 Entry가 가진 근거는 제목과 500자로 자른 요약뿐이다.
원문이 사라지거나 바뀌면 복구할 수 없다. ADR-0011 결정 2는 읽기 버튼으로 가져온 본문을 저장하지 않는다고 했고,
`GET /api/entries/:entryId/reader`(`apps/backend/src/server/entry-routes.ts`)는 본문을 응답만 하고 버린다.

신호도 부족하다. `opened_at`은 "앱에서 펼침"과 "원문 링크 클릭"을 함께 찍는다. 읽기 버튼으로 본문을 실제로 가져왔는지는 구분되지 않는다.
읽음·본문 같은 신호는 나중에 소급해서 만들 수 없다.

## 결정

1. **읽음 신호**: `entry.reader_fetched_at`(Reader Fetched At)에 읽기 버튼으로 본문을 **처음** 가져온 시각을 남긴다. `opened_at`과 같은 방식이라 다시 가져와도 바뀌지 않는다.
   신호의 강도는 지나감(Read Cursor) < 열었음(Opened At) < 본문 읽음(Reader Fetched At) < Bookmark 순이다.
2. **본문 저장**: 읽기 버튼으로 가져온 Entry에 한해 Markdown을 `entry_content`(`entry_id` PK·FK, `markdown`, `fetched_at`)에 저장한다.
   `entry_translation`처럼 Entry와 1:1인 별도 테이블이다. 목록에서 지나가기만 한 Entry는 저장하지 않는다.
3. **다시 가져오면 덮어쓴다**: 읽기 버튼은 지금처럼 부를 때마다 원문을 다시 가져온다(ADR-0011 결정 1). 성공하면 `markdown`과 `fetched_at`을 최신으로 바꾼다. 저장한 본문으로 응답하지 않는다.
4. **실패는 저장하지 않는다**: 원문을 받지 못했거나 본문이 비어 502로 응답하면 `entry_content`도 `reader_fetched_at`도 건드리지 않는다.
5. **원티드도 같은 경로다**: 원티드 공고 본문(ADR-0013)은 같은 `readOriginal`이 `ReaderView`로 만들므로 같은 코드로 저장한다. 본문을 만든 방식이 달라도 저장 경로는 하나다.
6. **조회**: 목록·Bookmark·Entry 조회 응답(`entryViewColumns`)에는 본문을 섞지 않는다. `entry_content`는 본문이 필요한 곳에서만 읽는다. 컬럼 타입은 `TEXT`이고 인덱스는 걸지 않는다.
7. **기존 데이터**: 과거에 읽기 버튼을 눌렀는지는 기록이 없다. 기존 Entry의 `reader_fetched_at`은 `NULL`이고, `NULL`은 "기록 이전이거나 읽지 않음"이다. `opened_at`으로 추정하지 않는다.

## 검토한 대안들

### `opened_at`으로 읽음을 추정한다

- 장점: 마이그레이션이 필요 없다.
- 단점: "펼침"과 "본문 읽음"이 섞여 있어 과거 값을 읽음으로 보면 신호가 오염된다.
- 기각 사유: 구분되지 않는 신호는 쓸 수 없다. 기록은 지금부터 시작한다.

### 본문을 `entry` 컬럼으로 둔다

- 장점: JOIN이 없다.
- 단점: 모든 Entry 조회에 큰 `TEXT`가 따라올 위험이 있다. `entry`는 정보원에서 가져온 것과 읽기 상태를 담고, 본문은 우리가 만든 파생 데이터다.
- 기각 사유: 번역을 `entry_translation`으로 나눈 것과 같은 이유다(ADR-0011).

### 저장한 본문으로 다시 응답한다

- 장점: 같은 글을 다시 열 때 원문 사이트에 요청이 가지 않는다.
- 단점: 원문이 고쳐져도 오래된 본문이 보이고, 캐시 만료 규칙이 필요하다.
- 기각 사유: 이 결정의 목적은 AI에게 넘길 근거 보관이지 읽기 속도가 아니다.

## 이유

ADR-0011이 본문 저장을 기각한 이유는 "대부분은 제목만 보고 넘기는데 전부 긁을 이유가 없다"였다. 읽기 버튼을 누른 소수만 저장하면 이 이유에 걸리지 않는다.
양은 하루 몇 건이고, 이미 가져온 Markdown을 저장하는 것이라 원문 사이트에 가는 요청은 늘지 않는다.
Postgres의 `TEXT`는 긴 값을 자동으로 압축하므로 따로 압축하지 않는다.

## 결과

- ADR-0011 결정 2("추출 결과는 저장하지 않는다")와 ADR-0013 결정 2의 "본문은 저장하지 않는다"를 이 결정이 대체한다. 두 ADR의 나머지 결정은 그대로다.
- Entry는 여전히 링크와 메타데이터다. 본문은 Entry의 일부가 아니라 읽기 버튼을 누른 Entry에 딸린 파생 데이터다(CONTEXT.md). 요약 500자 상한도 그대로다.
- 읽기 버튼 클릭은 Bookmark보다 약한 신호다. 실수로 눌렀거나 훑다 닫을 수 있어 가중치는 소비하는 쪽(AI)이 정한다.
- 이 결정은 쓰는 쪽만 만든다. 선호를 판단하는 AI, 본문 요약·태그 추출, 본문 전문 검색은 만들지 않는다. 본문을 저장해 두면 나중에 만들 수 있다.
- 북마크한 Entry의 본문을 과거분까지 채우는 백필은 하지 않는다. 필요해지면 외부 요청이 들어가므로 마이그레이션이 아니라 별도 스크립트로 만든다.
- 저장한 본문은 API로 내보내지 않는다. 본문을 읽는 소비자가 생길 때 그 경계를 정한다.
